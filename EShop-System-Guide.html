دليل سيستم EShop - الشرح المعماري الشامل

هذا الدليل تم تصميمه خصيصاً عشان يغطي كل تفصيلة في الـ System من الصفر ولحد أعقد نقطة زي الـ RabbitMQ. الدليل ده هيكون مرجعك الأساسي قبل وأثناء الانترفيو عشان تقدر ترد بثقة على أي سؤال، لأنك هتكون فاهم الكود شغال إزاي تحت الكبوت.

1. نظرة عامة على السيستم (System Overview & Architecture)

المشروع ده مبني بـ ASP.NET Core 10 وبيعتمد على معمارية اسمها Modular Monolith، وهي معمارية قوية جداً بتجمع بين بساطة الـ Monolith وقوة الـ Microservices في التنظيم.

شكل المشروع (Solution Structure):

EShop/
├── Bootstrapper/
│   └── Eshop.API/          ← الـ Host الرئيسي اللي بيشغل كل حاجة
├── Modules/
│   ├── Catalog/             ← موديول المنتجات (مستقل)
│   ├── Basket/              ← موديول السلة (مستقل)
│   └── Ordering/            ← موديول الطلبات (مستقل)
├── Shared/
│   ├── Shared/              ← الكلاسات الأساسية (DDD, Behaviors)
│   ├── Shared.Contracts/    ← الحاجات اللي الـ Modules بتكلم بعض بيها (DTOs, Queries)
│   └── Shared.Messaging/    ← الـ RabbitMQ و MassTransit
└── docker-compose.yml       ← البنية التحتية
ليه استخدمنا Modular Monolith ومش Microservices؟
  • الـ Microservices بتضيف تعقيدات كبيرة (Network latency, Distributed Transactions, Deployment Complexity).
  • الـ Modular Monolith بيخلينا نقسم الكود لـ Modules مستقلة (زي الـ Microservices بالظبط في الديزاين) بس في النهاية بنعملها Deploy كبرنامج واحد (Single Process).
  • يعني بنستفيد من التنظيم العالي بدون ما ندفع ضريبة الـ Microservices. ولما المشروع يكبر جداً، نقدر ببساطة نفصل أي Module ونخليه Microservice حقيقية لأن الكود أصلاً مفصول.

أهم التقنيات المستخدمة: Domain-Driven Design (DDD), CQRS Pattern, Vertical Slice Architecture, RabbitMQ (MassTransit), PostgreSQL, Redis, Minimal APIs (Carter).

2. الـ Domain-Driven Design (DDD) Building Blocks

الـ DDD مش مجرد فولدرات، هو طريقة تفكير عشان نخلي الكود يعكس البيزنس الحقيقي. في فولدر Shared.DDD إحنا بنينا الأساسيات اللي أي Entity أو Aggregate بيمشي عليها.

1. الـ Entities (الكائنات):

الـ Entity هو أي حاجة ليها Identity (رقم تعريفي) مميز. يعني لو عندي اتنين Products نفس الاسم ونفس السعر بس الـ Id مختلف، يبقوا حاجتين مختلفتين.

public interface IEntity<TId> : IEntity
{
    public TId Id { get; set; }
}

public interface IEntity
{
    // دول بنسميهم Audit Properties (عشان نعرف مين عمل ايه وامتى)
    public string? CreatedBy { get; set; }
    public DateTime? CreatedAt { get; set; }
    public string? LastModifiedBy { get; set; }
    public DateTime? LastModifiedAt { get; set; }
}

public abstract class Entity<TId> : IEntity<TId>
{
    public TId Id { get; set; }
    public string? CreatedBy { get; set; }
    public DateTime? CreatedAt { get; set; }
    public string? LastModifiedBy { get; set; }
    public DateTime? LastModifiedAt { get; set; }
}

2. الـ Domain Events (أحداث البيزنس):

لما حاجة مهمة تحصل في النظام (زي إن منتج يتضاف أو سعره يتغير)، بنعمل حدث (Event) عشان نبلغ باقي الكود. الـ IDomainEvent بيورث من INotification الخاص بـ MediatR عشان يقدر يتعامل معاه وينشره في الميموري.

public interface IDomainEvent : INotification
{
    Guid EventId => Guid.NewGuid();
    public DateTime OccurredOn => DateTime.UtcNow;
    public string EventType => GetType().AssemblyQualifiedName!;
}

3. الـ Aggregate Root (الجذور المجمعة):

الـ Aggregate Root هو نوع خاص من الـ Entities، بيمثل الباب الرئيسي لأي تعديل في مجموعة مترابطة. مفيش أي تعديل بيحصل إلا من خلاله عشان نحافظ على الـ Data Consistency. الـ Aggregate Root كمان بيكون جواه لستة للـ Domain Events اللي حصلت فيه.

public interface IAggregate : IEntity
{
    IReadOnlyList<IDomainEvent> DomainEvents { get; }
    IDomainEvent[] ClearDomainEvents();
}

public abstract class AggregateRoot<TId> : Entity<TId>, IAggregate<TId>
{
    private readonly List<IDomainEvent> _domainEvents = [];
    public IReadOnlyList<IDomainEvent> DomainEvents => _domainEvents.AsReadOnly();

    public IDomainEvent[] ClearDomainEvents()
    {
        var events = _domainEvents.ToArray();
        _domainEvents.Clear();
        return events;
    }
    
    protected void AddDomainEvent(IDomainEvent domainEvent)
    {
        _domainEvents.Add(domainEvent);
    }
}
الخلاصة: الـ Entity ليه ID. الـ Aggregate Root هو Entity كبير بيحمي نفسه وبيسجل الأحداث (Domain Events) اللي بتحصل جواه.

3. مثال الـ Product Aggregate (تطبيق عملي)

خلينا نشوف الـ Product إزاي بيطبق المفاهيم دي في الكود الحقيقي:

public class Product : AggregateRoot<Guid>
{
    // Properties كلها private set عشان نمنع أي تعديل عشوائي من برة (Encapsulation)
    public string Name { get; private set; } = default!;
    public List<string> Category { get; private set; } = default!;
    public string Description { get; private set; } = default!;
    public string ImageFile { get; private set; } = default!;
    public decimal Price { get; private set; }
    
    // Static Factory Method لإنشاء المنتج بدل الـ Constructor
    public static Product Create(Guid id, string name, List<string> category, string description, string imageFile, decimal price)
    {
        ArgumentException.ThrowIfNullOrEmpty(name);
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(price);
        
        var product = new Product
        {
            Id = id, Name = name, Category = category,
            Description = description, ImageFile = imageFile, Price = price,
        };
        
        // أول ما ننشئ المنتج، بنسجل إن الحدث ده حصل
        product.AddDomainEvent(new ProductCreatedEvent(product));
        return product;
    }
    
    // دالة لتعديل المنتج
    public void Update(string name, List<string> category, string description, string imageFile, decimal price)
    {
        ArgumentException.ThrowIfNullOrEmpty(name);
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(price);
        
        Name = name; Category = category;
        Description = description; ImageFile = imageFile;
        
        // لو السعر اتغير فعلاً، بنضيف حدث جديد عشان نبلغ النظام (مهم جداً عشان تحديث السلة لاحقاً!)
        if (Price != price)
        {
            Price = price;
            AddDomainEvent(new ProductPriceChangedEvent(this));
        }
    }
}
نقاط مهمة للإنترفيو:
1. ليه بنستخدم private set؟ عشان نحافظ على الـ Encapsulation. محدنش يقدر يعدل سعر المنتج مباشرة `product.Price = 50`، لازم يستخدم دالة Update اللي بتعمل Validation وبتضيف Event.
2. ليه Static Factory Method؟ عشان بتخلي الكود مقروء أكتر (Product.Create) وبتدينا مكان واضح نحط فيه شروط الإنشاء والـ Events.

الـ Events الخاصة بالمنتج بسيطة جداً وهي عبارة عن Records:

public record ProductCreatedEvent(Product Product) : IDomainEvent;
public record ProductPriceChangedEvent(Product Product) : IDomainEvent;

4. نمط CQRS مع MediatR

الـ CQRS (Command Query Responsibility Segregation) بيفصل عمليات القراءة (Queries) عن عمليات الكتابة والتعديل (Commands). إحنا هنا مستخدمين الـ Interfaces دي كـ Wrappers فوق MediatR عشان نوضح الـ Intent.

// Commands (كتابة أو تعديل - بترجع Response أو Unit)
public interface ICommand : IRequest<Unit> { }
public interface ICommand<out TResponse> : IRequest<TResponse> { }
public interface ICommandHandler<in TCommand, TResponse>
    : IRequestHandler<TCommand, TResponse>
    where TCommand : ICommand<TResponse>
    where TResponse : notnull { }

// Queries (قراءة فقط)
public interface IQuery<out TResponse> : IRequest<TResponse> { }
public interface IQueryHandler<in TQuery, TResponse>
    : IRequestHandler<TQuery, TResponse>
    where TQuery : IQuery<TResponse>
    where TResponse : notnull { }
ليه التغليف (Wrappers) ده؟
1. الوضوح (Semantic clarity): مجرد ما تبص على الكلاس هتعرف هو Command ولا Query.
2. القيود (Constraints): بنقدر نطبق Pipeline Behaviors على الـ Commands بس ومطبّقهاش على الـ Queries (زي الـ Validation مثلاً).

مثال كامل للـ CreateProduct:

الـ Flow بيبدأ من الـ Carter Endpoint، بيبعت Command لـ MediatR، والـ Handler بينفذ البيزنس.

// 1. الـ Endpoint (Carter)
public class CreateProductEndPoint : ICarterModule
{
    public void AddRoutes(IEndpointRouteBuilder app)
    {
        app.MapPost("/products", async (CreateProductRequest request, ISender sender) =>
        {
            var command = request.Adapt<CreateProductCommand>(); // Mapster
            var result = await sender.Send(command); // MediatR
            var response = result.Adapt<CreateProductResponse>();
            return Results.Created($"/products/{response.ProductId}", response);
        });
    }
}

// 2. الـ Command والـ Handler
public record CreateProductCommand(ProductDto Product) : ICommand<CreateProductResult>;
public record CreateProductResult(Guid ProductId);

public class CreateProductHandler(CatalogDbContext _context) 
    : ICommandHandler<CreateProductCommand, CreateProductResult>
{
    public async Task<CreateProductResult> Handle(CreateProductCommand request, CancellationToken cancellationToken)
    {
        var product = Product.Create(Guid.NewGuid(), request.Product.Name, ...);
        _context.Products.Add(product);
        await _context.SaveChangesAsync(cancellationToken);
        return new CreateProductResult(product.Id);
    }
}

// 3. الـ Validator (هيشتغل أوتوماتيك عبر الـ Pipeline Behavior)
public class CreateProductCommandValidator : AbstractValidator<CreateProductCommand>
{
    public CreateProductCommandValidator()
    {
        RuleFor(x => x.Product).NotNull().WithMessage("Product is required");
        RuleFor(x => x.Product.Name).NotEmpty();
        RuleFor(x => x.Product.Price).GreaterThan(0);
    }
}

5. الـ Pipeline Behaviors في MediatR

الـ Pipeline Behaviors عاملة زي الـ Middleware بس جوا MediatR. بتنفذ كود معين قبل وبعد كل Handler.

1. الـ ValidationBehavior:

public class ValidationBehavior<TRequest, TResponse>(IEnumerable<IValidator<TRequest>> validators) 
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : ICommand<TResponse> // ⚠️ ركز هنا!
{
    public async Task<TResponse> Handle(TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken cancellationToken)
    {
        var context = new ValidationContext<TRequest>(request);
        var validationResult = await Task.WhenAll(validators.Select(v => v.ValidateAsync(context, cancellationToken)));
        var failures = validationResult.Where(r => r.Errors.Any()).SelectMany(r => r.Errors).ToList();
        
        if (failures.Any())
            throw new ValidationException(failures);
            
        return await next(cancellationToken);
    }
}
لاحظ إننا حطينا شرط where TRequest : ICommand. ده معناه إن أي Query مش هتدخل جوا الـ Validation Pipeline لأن الـ Queries مجرد قراءة ومش محتاجة Validation معقد يرمي Exceptions بالطريقة دي.

2. الـ LoggingBehavior:

public class LoggingBehavior<TRequest, TResponse>(ILogger<LoggingBehavior<TRequest, TResponse>> logger)
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull, IRequest<TResponse>
    where TResponse : notnull
{
    public async Task<TResponse> Handle(TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken cancellationToken)
    {
        logger.LogInformation("[Start]Handling {RequestName}", typeof(TRequest).Name);
        var timer = Stopwatch.StartNew();
        
        var response = await next();
        
        timer.Stop();
        if (timer.Elapsed.Seconds > 3)
            logger.LogWarning("Handling {RequestName} took {TimeTaken}", typeof(TRequest).Name, timer.Elapsed);
            
        logger.LogInformation("[End]Handled {RequestName}", typeof(TRequest).Name);
        return response;
    }
}

الـ Logging بيشتغل على كل الـ Requests (Commands + Queries). بيسجل بداية ونهاية العملية، ولو أخدت أكتر من 3 ثواني بيعمل Warning.

6. الـ Domain Events الداعمة In-Memory

دي من أهم النقط في السيستم. إزاي السيستم بيعرف إن في حاجة حصلت جوا الـ Aggregate وبينشرها؟

The Complete Flow (إزاي الأحداث بتشتغل):

  1. الـ البيزنس بيتنفذ (مثلاً بنعدل سعر المنتج عن طريق Product.Update()).
  2. جوا الـ Update بيتم استدعاء AddDomainEvent(new ProductPriceChangedEvent(this)). ده بيضيف الحدث للستة داخلية جوه الكائن.
  3. بنعمل SaveChangesAsync() على الـ DbContext.
  4. وهنا بييجي دور الـ Interceptor اللي بيوقف عملية الحفظ لحظة قبل ما يبعت الداتا للداتا بيز.
public class DispatchDomainEventInterceptor(IMediator _mediator) : SaveChangesInterceptor
{
    public override async ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result, CancellationToken cancellationToken = default)
    {
        // 1. قبل الحفظ، بننشر الأحداث
        await DispatchDomainEvent(eventData.Context);
        
        // 2. بنكمل عملية الحفظ الطبيعية
        return await base.SavingChangesAsync(eventData, result, cancellationToken);
    }
    
    private async Task DispatchDomainEvent(DbContext? context)
    {
        if (context is null) return;
        
        // 1. بنجيب كل الـ Aggregates اللي حصل فيها تغيير من الـ ChangeTracker
        var aggregate = context.ChangeTracker.Entries<IAggregate>().Select(a => a.Entity);
        
        // 2. بنجمع كل الـ Domain Events من الـ Aggregates دي
        var domainEvents = aggregate.SelectMany(a => a.DomainEvents).ToList();
        
        // 3. بنمسح الأحداث من الـ Aggregates عشان ميتعملهاش نشر مرتين
        aggregate.ToList().ForEach(domainEvent => domainEvent.ClearDomainEvents());
        
        // 4. بننشر كل حدث باستخدام MediatR
        foreach (var domainEvent in domainEvents)
            await _mediator.Publish(domainEvent); // ⚠️ IN-MEMORY PUBLISH
    }
}
خلي بالك جداً في الانترفيو: الـ Domain Events بتشتغل In-Memory (في نفس الـ Process) عن طريق MediatR. هي مش بتروح للـ RabbitMQ نهائي في المرحلة دي! MediatR بيدور على أي كلاس بيعمل Implement لـ INotificationHandler وبينفذه.

كمان عندنا الـ AuditableEntityInterceptor:

عشان منكررش كود الـ CreatedAt و CreatedBy في كل حتة، بنستخدم Interceptor تاني بيكتبهم أوتوماتيك.

public class AuditableEntityInterceptor(IHttpContextAccessor _httpContextAccessor) : SaveChangesInterceptor
{
    private void UpdateEntitys(DbContext? context)
    {
        var entries = context.ChangeTracker.Entries<IEntity>();
        var user = _httpContextAccessor.HttpContext?.User.FindFirst(ClaimTypes.NameIdentifier)?.Value ?? "System";
        
        foreach (var entry in entries)
        {
            if (entry.State == EntityState.Added)
            {
                entry.Entity.CreatedBy = user;
                entry.Entity.CreatedAt = DateTime.UtcNow;
                entry.Entity.LastModifiedBy = user;
                entry.Entity.LastModifiedAt = DateTime.UtcNow;
            }
            else if (entry.State == EntityState.Modified || entry.HasChangedOwendEntities())
            {
                entry.Entity.LastModifiedBy = user;
                entry.Entity.LastModifiedAt = DateTime.UtcNow;
            }
        }
    }
}

7. الـ Integration Events (RabbitMQ + MassTransit) - نقطة الوصل!

دي أهم نقطة عشان تفهم السيستم كله، إيه الفرق بين الـ Domain Event والـ Integration Event؟ وإزاي بنربطهم؟

المقارنة Domain Event Integration Event
الـ Scope (المدى) جوا نفس الـ Module ونفس الـ Process عابر للـ Modules والـ Processes (Cross-Module)
الوسيط (Transport) MediatR (In-Memory) RabbitMQ عبر MassTransit
الـ Interface IDomainEvent : INotification IntegrationEvent (Record)
المُستقبِل (Handler) INotificationHandler<T> IConsumer<T> الخاص بـ MassTransit
حجم الداتا ممكن يبعت الـ Entity كامل بحالته بيبعت شوية Primitive Data بس (JSON) عشان تقليل الحجم

الـ Bridge (الجسر بين الـ Domain والـ Integration):

لما الـ Interceptor بينشر الحدث عن طريق MediatR، في Handler مخصوص بيسمعله عشان يحوله لـ Integration Event ويبعته لـ RabbitMQ.

public class ProductPriceChangedEventHandler(IBus bus, ILogger<ProductPriceChangedEventHandler> logger) 
    : INotificationHandler<ProductPriceChangedEvent>
{
    public async Task Handle(ProductPriceChangedEvent notification, CancellationToken cancellationToken)
    {
        // 1. استقبلنا الحدث من MediatR
        
        // 2. بنعمل Map للبيانات المهمة بس في كلاس جديد
        var integrationEvent = new ProductPriceChangedIntegrationEvent
        {
            ProductId = notification.Product.Id,
            Name = notification.Product.Name,
            Categories = notification.Product.Category,
            Description = notification.Product.Description,
            ImageUrl = notification.Product.ImageFile,
            Price = notification.Product.Price,
        };
        
        // 3. بننشره على RabbitMQ عن طريق MassTransit
        await bus.Publish(integrationEvent, cancellationToken);  // ⚠️ ده بيروح لـ RabbitMQ
    }
}

الـ Consumer (ازاي موديول الـ Basket بيستقبل التغيير؟):

في الـ Basket Module، عندنا كلاس بيعمل Implement لـ IConsumer من MassTransit بيستنى أي رسالة تيجي من RabbitMQ.

public class ProductPriceChangedIntegrationEventHandler(ISender sender, ILogger<...> logger) 
    : IConsumer<ProductPriceChangedIntegrationEvent>  // ⚠️ لاحظ إن ده مش MediatR
{
    public async Task Consume(ConsumeContext<ProductPriceChangedIntegrationEvent> context)
    {
        // استقبلنا الرسالة من RabbitMQ
        
        // بنبعت Command جوا הـ Basket Module عشان يعدل الأسعار عنده
        var result = await sender.Send(
            new UpdateItemPriceBasketCommand(context.Message.ProductId, context.Message.Price));
            
        // Handler بتاع الكوماند ده هو اللي بيروح يـ Update الداتا بيز ويمسح الـ Redis Cache
    }
}

إعدادات MassTransit (الـ Config):

public static IServiceCollection AddMassTransitWithAssmblies(this IServiceCollection services, 
    IConfiguration configuration, params Assembly[] assemblies)
{
    services.AddMassTransit(config =>
    {
        // دي دالة سحرية بتخلي اسامي الـ Queues بـ kebab-case بناءً على اسم الكلاس!
        config.SetKebabCaseEndpointNameFormatter(); 
        
        config.SetInMemorySagaRepositoryProvider();
        
        // بيدور في كل الـ Assemblies على أي كلاس عامل IConsumer وبيسجله أوتوماتيك
        config.AddConsumers(assemblies); 
        
        config.UsingRabbitMq((context, cfg) =>
        {
            cfg.Host(configuration["MessageBroker:Host"], host =>
            {
                host.Username(configuration["MessageBroker:Username"]!);
                host.Password(configuration["MessageBroker:Password"]!);
            });
            
            // بيعمل Auto-wiring (بيعمل Queues و Exchanges ويربطهم ببعض لكل الـ Consumers)
            cfg.ConfigureEndpoints(context);  
        });
    });
    return services;
}
دالة SetKebabCaseEndpointNameFormatter() بتخلي اسم الـ Queue بتاع الكلاس ProductPriceChangedIntegrationEventHandler يتحول أوتوماتيك لـ: product-price-changed-integration-event-handler على RabbitMQ.

8. شرح واجهة RabbitMQ (زي ما هي في صورك بالظبط!)

لو سألوك في الانترفيو عن الـ UI بتاع RabbitMQ وإيه الحاجات الغريبة اللي بتظهر فيه، دي الإجابة التفصيلية بناءً على صور الـ Screenshots بتاعتك.

شاشة الـ Overview:

  • Node (rabbit@ecommerce-mq): ده اسم الـ Host بتاع الكونتينر اللي شغال عليه RabbitMQ (الاسم جي من docker-compose).
  • File descriptors / Erlang processes: دي تفاصيل داخلية لـ Erlang (اللغة اللي مكتوب بيها RabbitMQ) بتوريك استهلاك الـ resources.
  • Memory (145 MiB): استهلاك الرام للـ Node دي.

شاشة الـ Exchanges (الأهم!):

ليه عندنا Exchanges بالأسماء دي؟ وازاي MassTransit عملها؟

  • (AMQP default) - direct: ده الأساسي بتاع RabbitMQ، أي Queue بتتعمل بتتربط بيه تلقائياً باسمها.
  • Shared.Messaging.Events:IntegrationEvent - fanout: ده Exchange عام بيمثل الـ Base Class. MassTransit بيعمله تلقائياً عشان يدعم الـ Polymorphism (لو حبيت تسمع لأي Event بيورث من ده).
  • Shared.Messaging.Events:ProductPriceChangedIntegrationEvent - fanout: ده الـ Exchange الخاص بالرسالة بتاعتنا. لما بنعمل bus.Publish()، الرسالة بتروح للـ Exchange ده الأول. ونوعه Fanout يعني هيبعت الرسالة لأي حاجة مربوطة بيه.
  • product-price-changed-integration-event-handler - fanout: ده الـ Exchange الخاص بالـ Consumer. إيه ده؟ هو الـ Consumer ليه Exchange؟ أيوة! MassTransit بيعمل Exchange-to-Exchange Binding.
  • الباقي زي amq.direct, amq.topic... دول Exchanges أساسية من RabbitMQ نفسه ومبنيجيش ناحيتهم.
سر خطير للـ Interview: ليه MassTransit بيعمل Exchange-to-Exchange Binding؟
MassTransit مش بيربط الـ Exchange بتاع الرسالة بالـ Queue مباشرة! بيعمل كدا:
Message Exchange ➔ Consumer Exchange ➔ Consumer Queue

السبب: عشان لو عندك أكتر من كلاس (Consumer) في أكتر من ميكروسيرفيس عاوزين يسمعوا نفس الرسالة، يبقى كل Consumer ليه الـ Exchange والـ Queue الخاصين بيه، ويتربطوا كلهم بالـ Exchange الرئيسي بتاع الرسالة، فكل واحد توصله نسخة مستقلة من غير ما يتأثروا ببعض!

10. سلة المشتريات (Basket) و نمط הـ Decorator في הـ Caching

في موديول الـ Basket، احنا بنستخدم نمط الـ Decorator Pattern عشان نضيف خاصية الكاشينج (Caching) من غير ما نعدل في كود الـ Repository الأصلي، وده تطبيق عظيم لمبدأ الـ Open/Closed Principle.

// في ملف BasketModule.cs
services.AddScoped<IBasketRepository, BasketRepository>();
services.Decorate<IBasketRepository, CachedBasketRepository>();

بنستخدم مكتبة Scrutor (عن طريق أمر Decorate) عشان تعمل الآتي: أي كلاس هيطلب IBasketRepository في الـ Constructor، هياخد نسخة من CachedBasketRepository، والـ Cached بدوره هياخد نسخة من الـ BasketRepository الأصلي يكلمه لو ملقاش الداتا في الـ Redis.

public class CachedBasketRepository(
    IBasketRepository _basketRepository,  // ده الـ Original
    IDistributedCache _distributedCache) : IBasketRepository
{
    public async Task<ShoppingCart> GetBasketAsync(string userName, bool asNoTracking = true, CancellationToken cancellationToken = default)
    {
        // 1. بندور في الـ Redis الاول
        var cachedJson = await _distributedCache.GetStringAsync(cacheKey, cancellationToken);
        if (cachedJson is not null)
        {
            return Deserialize(cachedJson); // Cache Hit
        }

        // 2. لو ملقيناهوش، بنكلم الـ Original Repository يجيبه من الـ DB
        var basket = await _basketRepository.GetBasketAsync(userName, asNoTracking, cancellationToken);
        
        // 3. نحفظه في الكاش للمرات الجاية
        await SetCacheAsync(cacheKey, basket, cancellationToken);
        
        return basket;
    }
}
ولما بيحصل تحديث (زي الـ Integration Event بتاع تغيير السعر ما بيضرب)، الـ Handler بيروح يمسح الكاش بتاع اليوزرز اللي اتأثروا، عشان المرة الجاية يجيبوا الداتا الجديدة من الداتا بيز وبعدين تتكيش تاني.

11. التواصل بين الـ Modules (Cross-Module Communication)

عندنا نوعين من التواصل بين الـ Modules (مثلاً Basket عايز يكلم Catalog):

1. تواصل متزامن (Synchronous - In-Process):

لو الـ Basket عايز بيانات منتج عشان ينفذ عملية دلوقتي حالاً (مثلاً اليوزر بيضيف منتج للسلة ومحتاجين نجيب سعره واسمه). بنعمل ده عن طريق MediatR ومكتبة Catalog.Contracts.

// جوا Basket Handler
var result = await sender.Send(new GetProductByIdQuery(request.ProductId)); 
// الـ Query متعرف في Shared Contracts، والـ Handler بتاعه عايش في الـ Catalog! MediatR بيوصلهم ببعض In-Memory

2. تواصل غير متزامن (Asynchronous - Message Broker):

لو الـ Catalog غير سعر منتج، وعايز يبلغ الـ Basket عشان يعدل السلات اللي فيها المنتج ده (بدون ما يعطّل نفسه). بنعمل ده عن طريق الـ Integration Events و RabbitMQ زي ما شرحنا فوق.

12. الـ Bootstrapper (نقطة التجميع)

في الـ Modular Monolith، كل Module بيكون مستقل (كلاس لايبراري لوحده). الـ Eshop.API هو الـ Host Project اللي بيلمهم كلهم مع بعض عشان يشتغلوا كبرنامج واحد.

var builder = WebApplication.CreateBuilder(args);

// 1. جلب הـ Assemblies بتاعت كل الـ Modules
var CatalogAssembly = typeof(CatalogModule).Assembly;
var BasketAssembly = typeof(BasketModule).Assembly;
var OrderingAssembly = typeof(OrderingModule).Assembly;

// 2. تسجيل الخدمات المشتركة لكل הـ Assemblies بخبطة واحدة!
builder.Services.AddCarterWithAssmblies(CatalogAssembly, BasketAssembly, OrderingAssembly);
builder.Services.AddMediatRWithAssmblies(CatalogAssembly, BasketAssembly, OrderingAssembly);
builder.Services.AddMassTransitWithAssmblies(builder.Configuration, CatalogAssembly, BasketAssembly, OrderingAssembly);

// 3. تسجيل الـ Interceptors (الـ Domain Events)
builder.Services.AddScoped<ISaveChangesInterceptor, AuditableEntityInterceptor>();
builder.Services.AddScoped<ISaveChangesInterceptor, DispatchDomainEventInterceptor>();

// 4. استدعاء دوال التسجيل الخاصة بكل Module
builder.Services
    .AddCatalogModule(builder.Configuration)
    .AddBasketModule(builder.Configuration)
    .AddOrderingModule(builder.Configuration);

var app = builder.Build();

// 5. تهيئة الـ Modules (تطبيق الـ Migrations وعمل Seeding)
await app.UseCatalogModuleAsync();
await app.UseBasketModuleAsync();
await app.UseOrderingModuleAsync();

app.Run();
هنا بتظهر قوة الـ Modular Monolith: الـ Program.cs نضيف جداً. كل Module مسئول عن خدماته، والـ Bootstrapper مجرد مجمع بياخد الـ Configurations ويركبهم جنب بعض.

13. أسئلة المقابلة (Interview Q&A) وإجاباتها النموذجية

دي تجميعة لأهم الأسئلة اللي ممكن تتسألها بناءً على الأركيتكتشر اللي أنت عملتها، مع الإجابة اللي تبينك فاهم جداً (Senior Level):

س 1: إيه الفرق بين الـ Domain Event والـ Integration Event؟ وليه مستخدمش واحد بس؟

الإجابة: الـ Domain Event بيحصل جوا نفس الباوندري (نفس الموديول) وبيتنشر In-Memory باستخدام MediatR، وممكن يتبعت فيه الكائن كامل (زي Product) عشان الـ Handlers اللي معاه في نفس الموديول يتصرفوا.
أما الـ Integration Event ده بنستخدمه لما نعوز نكلم موديول تاني أو سيستم تاني. ده بيتبعت عبر Message Broker (RabbitMQ)، ولازم يكون خفيف جداً ومفيهوش كائنات معقدة (Primitive types بس) لتقليل حجم الـ Payload وتجنب الـ Coupling. بنحول الـ Domain Event لـ Integration Event عشان نكلم العالم الخارجي.

س 2: إزاي بتضمن إن الـ Domain Events تتنفذ قبل ما الداتا تتحفظ فعلاً؟

الإجابة: بستخدم الـ SaveChangesInterceptor الخاص بـ EF Core. بعمل Override لدالة SavingChangesAsync، وقبل ما أنادي الـ Base method، بجيب كل الـ Aggregates اللي حصلها Track وفيها Events، بمسح Events دي منها وببعتها لـ MediatR.Publish عشان الـ Handlers تتنفذ. ولما كله يخلص، الداتا بتتحفظ.

س 3: ليه بتفصل الـ Commands عن الـ Queries (CQRS) مع إنهم على نفس الداتا بيز؟

الإجابة: الـ CQRS حتى لو على داتا بيز واحدة (Logical Separation) بيفيدني في الـ Separation of Concerns. الـ Commands بيبقى فيها Business Logic معقد و Validation، بينما الـ Queries بتبقى بسيطة وممكن ترجع DTOs مباشرة باستخدام AsNoTracking أو حتى أكلم الداتا بيز بـ Dapper لو حبيت أسرعها. كمان بيفيدني إني أقدر أحط Behaviors معينة (زي الـ Validation) على الـ Commands بس.

س 4: إيه هو الـ Outbox Pattern وهل هو متطبق في السيستم بتاعك؟

الإجابة: السيستم الحالي مفيهوش Outbox Pattern. حالياً احنا بنبعت الـ Integration Event مباشرة لـ RabbitMQ جوا الـ Handler. الـ Outbox Pattern بيحل مشكلة الـ Dual Write (إن الداتا تتحفظ في الداتا بيز بس الرسالة تقع قبل ما توصل RabbitMQ). عشان أطبقه، المفروض أحفظ الـ Event في جدول في الداتا بيز (Outbox Table) في نفس الـ Transaction بتاعة البيزنس، ويكون فيه Background Worker بيقرا الجدول ده ويبعت لـ RabbitMQ. (قولها كدا هتبين إنك عارف العيوب وازاي تحلها!).

س 5: إزاي بتطبق الـ Caching في الـ Basket وليه استخدمت Scrutor؟

الإجابة: طبقت الـ Cache-Aside pattern باستخدام الـ Decorator Pattern. الـ CachedBasketRepository بيعمل Wrap للـ BasketRepository الأصلي. استخدمت Scrutor عشان بيسهل عملية الـ Dependency Injection بتاعة الـ Decorator من غير ما ألخبط الـ DI Container. لو الداتا مش في الـ Redis بنجيبها من الـ DB ونحطها في الكاش. ولما يحصل Update بنمسح الكاش بتاع اليوزر ده (Invalidation).

س 6: ليه الـ Exchange بتاع الرسالة مربوط بـ Exchange تاني باسم الـ Consumer في RabbitMQ؟

الإجابة: دي تركاية بيعملها MassTransit. بدل ما يربط الـ Message Exchange بالـ Queue مباشرة، بيعمل Consumer Exchange في النص (Exchange-to-Exchange Binding). ده بيسمح بمرونة عالية (Topology Routing). لو عندي أكتر من سيرفيس أو Consumer محتاجين يسمعوا نفس الحدث، كل واحد بيتعمله Exchange يتربط بالأساسي، وكدة كل Consumer بياخد نسخته الخاصة من غير ما يؤثروا على بعض ولو consumer وقع مش هيوقع الباقي.

س 7: إيه هو الـ Modular Monolith وليه مش Microservices؟

الإجابة: الـ Modular Monolith هو كود متقسم لـ Modules مستقلة تماماً (زي الـ Microservices)، كل موديول ليه الـ DB Schema بتاعته وليه الباوندري بتاعه ومبيكلموش بعض مباشرة إلا عبر الـ Contracts أو الـ Events. لكن في النهاية بيتعملهم Deploy في Process واحدة (Host واحد). ده بيدينا ميزة التنظيم العالي وسهولة فصلهم مستقبلاً لـ Microservices، وفي نفس الوقت بيوفر علينا تعقيدات الشبكة والـ DevOps والـ Distributed Transactions اللي موجودة في الـ Microservices.

14. الفجوات الحالية والتحسينات المستقبلية (Filling the Gaps)

أي سيستم في الدنيا بيبدأ بنسخة مبدئية وبيحصل فيه تطور. عشان تبين في الانترفيو إنك مش بس كاتب كود، إنما كمان فاهم إيه اللي ناقصك وإزاي تطوره مستقبلاً (Senior Mindset)، دي أهم الـ Gaps اللي في السيستم حالياً واللي هنعالجها قدام:

1. غياب الـ Outbox Pattern (نقطة حرجة)

المشكلة: حالياً في الـ ProductPriceChangedEventHandler، احنا بنعمل Publish للرسالة على RabbitMQ مباشرة. لو الـ Message Broker كان واقع، الرسالة هتضيع والـ Basket مش هيعرف إن السعر اتغير!
الحل المستقبلي: تطبيق نمط الـ Transactional Outbox. هنحفظ الرسالة في جدول في الداتا بيز (Outbox Table) في نفس الـ Transaction، وبعدين Service تانية (Background Worker) تقرأ من الجدول ده وتبعت لـ RabbitMQ. ده بيضمن 100% إن الرسالة مش هتضيع.

2. التعامل مع الـ Idempotency (التكرار)

المشكلة: RabbitMQ بيضمن إن الرسالة توصل At-Least-Once، يعني ممكن جداً الرسالة توصل للـ Consumer مرتين (بسبب Network glitch). حالياً الـ Basket لو استقبل رسالة تغيير السعر مرتين، هيحدث الداتا بيز مرتين.
الحل المستقبلي: لازم نخلي الـ Consumers عندنا "Idempotent". يعني نسجل الـ EventId في جدول في الداتا بيز لما نستلمه، ولو الرسالة جت تاني بنفس الـ ID، نتجاهلها.

3. الـ Security و Keycloak (الخطوة الجاية!)

الوضع الحالي: الـ Endpoints بتاعتنا مفتوحة وأي حد يقدر يعمل Create Product أو يضيف في سلة المشتريات (مفيش Authentication).
الخطوة الجاية: هندمج Keycloak عشان يعمل Identity Provider للسيستم بتاعنا، ونستخدم OAuth2 + OpenID Connect (OIDC). السيستم هيستقبل JWT Token، ويحصلها Validation، ونتأكد من الـ Roles بتاعة اليوزر قبل ما ننفذ الـ Commands.

4. الـ Resiliency (المرونة ضد الأعطال) بـ Polly

الوضع الحالي: لو الـ Redis وقع، الـ Basket Repository هيضرب Exception ومش هيرد على اليوزر.
الحل المستقبلي: استخدام مكتبة Polly لعمل Retry Policy أو Circuit Breaker بحيث لو الـ Cache واقع، يقدر يكمل ويجيب الداتا من الـ DB من غير ما يوقع الـ Request.

أسئلة إضافية للمقابلة (المستوى المتقدم):

س 8: إزاي بتتعامل مع الـ Data Consistency بين أكتر من Module؟

الإجابة: بما إننا Modular Monolith وكل موديول ليه الـ DB Context بتاعه (Logical Separation)، مقدرش أعمل Database Transaction واحدة تجمعهم. عشان كده بستخدم الـ Eventual Consistency عن طريق الـ Integration Events. الـ Catalog بيحدث الداتا بتاعته، وبيبعت Event، والـ Basket بيحدث الداتا بتاعته لما يستلم الحدث. لو حصل فشل، لازم يكون عندي Retry Mechanism و Dead Letter Queue (DLQ) في RabbitMQ.

س 9: ليه استخدمت الـ Decorator Pattern للكاشينج ومستخدمتش الـ Middleware؟

الإجابة: الـ Middleware بيشتغل على مستوى الـ HTTP Request كله (برة الـ Application Layer). الـ Decorator بيشتغل جوا الـ Application Layer وبيعمل Wrap للـ Repository. ده أحسن بكتير لأنه بيفصل الـ Business Logic عن الـ Caching Logic (Single Responsibility Principle) وبيخليني أقدر أطبق الكاشينج من غير ما أغير أي كود في الـ Handlers أو في الـ Repository الأصلي (Open/Closed Principle).

س 10: إيه اللي بيحصل لو الـ Validation بتاع Command فشل؟

الإجابة: الـ ValidationBehavior في MediatR هيوقف الـ Request قبل ما يوصل للـ Handler أصلاً، وهيرمي ValidationException. بعد كده بييجي دور الـ Global Exception Handler (اللي متسجل في الـ Bootstrapper)، بيمسك الـ Exception ده ويحوله لـ Problem Details (Standard HTTP 400 Bad Request) ويرجعه لليوزر بشكل مرتب فيه كل الأخطاء.
